# Close the remaining 2.3 coverage gaps

This is the bounded execution checklist for hub tasks 0.2, 0.3 and 0.5.
Execution completed on 30 October 2026; see the [results](v2.3-coverage-results.md)
and [13-case index](v2.3-evidence-bundle.md#browsing-captures) (`tests/e2e-v2/results/closure-index-2026-10-30.json`).
This checklist does not replace the final acceptance run.

## Scope and evidence rules

Use a disposable local kind cluster with an explicit kubeconfig/context. Keep
the tested platform pinned: Kubernetes 1.35.0, RabbitMQ Cluster Operator 2.16.1,
RabbitMQ 4.4.0-management and Metrics Server 0.8.0. Run fixtures sequentially on
the local node and check capacity before each healthy-case workload.

The strict path supports the resource transitions actually demonstrated by the
fixture: paired CPU/memory requests and CPU limits, with a fixed memory ceiling.
Full in-place memory-limit support failed its broker-budget check. Changing that
ceiling requires explicitly enabled rolling fallback. Other platform versions
and resource-policy combinations remain unverified until separately tested.

Each case must record its image digest, policy hash, injection/removal times,
controller operation revision/stage/reason, custom-resource and template tuples,
Pod desired/effective resources, Pod/container identities and restart counts.
Retain the fault fixture and sanitized observations with checksums. Account for
confirmed message IDs whenever a case publishes traffic.

Use existing deterministic tests for exact fault behavior and arithmetic. Add
real-cluster evidence where Kubernetes/Operator behavior is the uncertainty.
Label controlled API responses as injected evidence; they do not establish how
the real metrics provider behaves. Never add production fault-injection flags
or require broker exec/Erlang commands for these tests.

## Task 0.3: Operator ordering and interrupted writes

Use temporary admission policies or narrowly scoped RBAC changes in the
disposable cluster. Restrict denial to the scaler identity, test namespace and
specific field/subresource; record the rule and its removal. Observe actual
StatefulSet strategy before accepting resource propagation as correctly ordered.

| Case | Interrupt or change | Required result | Existing evidence and remaining work |
|---|---|---|---|
| O-INTENT | Deny the controller's operation-state persistence | No strategy, custom-resource resource or Pod resize writes; restoring persistence permits a newly validated intent | `TestFailedIntentPersistencePreventsAllBrokerWrites`; add live denial and before/after API snapshots. |
| O-STRATEGY | Deny the custom-resource override that requests `OnDelete` | Durable intent remains; resources are untouched until the actual owned StatefulSet is observed using `OnDelete` after denial removal | `TestRetriedTemplateWriteRequiresObservedOnDelete`; add live strategy-denial recovery. |
| O-TEMPLATE | Permit `OnDelete`, then deny the custom-resource resource update | Operation/target survives; no Pod submission before the Operator template matches the target; removal converges the same operation | `TestTemplateWriteFailureRetainsIntentAndRetriesWithoutPodWrites`; add live resource-write-denial recovery. |
| O-PARTIAL | Deny only one broker's `pods/resize` update | Other brokers receive concurrent requests; accepted targets are not repeatedly submitted; the denied broker converges after the denial is removed | Existing recovery captures cover this, supersession and restarts. Include the corrected harness in the final immutable-build run. |
| O-DRIFT | Make a controlled external custom-resource or strategy edit while an operation is pending | Explicit conflict/block; the scaler does not adopt or overwrite an unrelated tuple as its own operation | `TestReviewSupersessionDoesNotAdoptExternalCR` and strategy-drift tests exist; add named live external-writer evidence. |
| O-REPLACE | Replace a broker during an unfinished operation through the Kubernetes API | Old UID/container samples cannot complete the operation; bind to the new identity, rebuild observation eligibility, then converge or explain the block | Existing rolling/restart captures exercise replacement. Add a targeted unfinished-operation assertion, including Operator-generated configuration and template changes. |

For each recoverable denial, verify the retained target and revision after
restart as well as after denial removal. Do not require recovery from an external
conflict by blindly overwriting the external writer. A clear, stable block with
an actionable reason is the correct result in that case.

The rolling strategy write also has a deterministic regression:
`TestRollingRetryRechecksSafetyAfterFailedStrategyWrite`. A retry must recheck
readiness and quorum shutdown guards; observing an already running rollout must
remain possible while a broker is temporarily unready.

Close 0.3 when the snapshots establish this order and its interruption behavior:

```text
durable intent -> observed OnDelete -> CR resources -> owned template -> Pod submissions -> effective convergence
```
