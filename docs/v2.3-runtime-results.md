# 2.3 runtime verification

Local source implementation is under verification on Kubernetes 1.35.0,
RabbitMQ Cluster Operator 2.16.1, RabbitMQ 4.4.0-management and Metrics Server 0.8.0.
Three persistent brokers run on one local kind node (4 CPUs, approximately 6 GiB).
This is not production evidence, a multi-node availability claim, or measured
infrastructure savings.

The initial run retained a completed idle feasibility fixture. Kubelet reported
`Deferred`: CPU requested800m, used3225m, capacity4000m. Two brokers applied;
the third held its accepted target until the idle fixture was removed. The
controller did not roll back successful changes or repeatedly patch the accepted
Pod target. Its original240s deadline miss remains in the evidence.

The fresh cycle checked projected requests before publishing. It completed
100m→800m→100m under the declared load/cooldown protocol with every confirmed
persistent message ID consumed and acknowledged. No discard-on-full policy or
queue purge was used. Quorum queues were explicitly declared.

This is a three-broker Operator topology. The retained native GKE experiment was
a single-broker StatefulSet with a managed VPA updater. It motivates the target;
it is not a matched performance comparison. A controlled native comparison on
the same topology/platform/workload has not been run.

## Runtime-discovered bookkeeping and harness fixes

The fresh cycle also exposed a redundant HIGH operation after the real HIGH
operation had converged under continued demand. It made no additional resize
requests but produced a later105.004s last-operation record. The first real
operation (revision1,100m→800m, one request per broker) completed in90.004s;
the no-op revision2 started from800m and made zero requests. Raw captures retain
both. The controller now clears the stale current-profile candidate at
convergence; a composed tracked regression checks that completion starts a fresh
down window and creates no duplicate operation.

The first recovery run reached its final LOW step, but its harness read the
previous completed MEDIUM record while LOW was still active. The resulting
interval assertion failed. Post-run inspection shows LOW revision9 started
105s after MEDIUM revision8 completed, satisfying the configured60s minimum.
The harness now requires no active operation before accepting terminal state.
The original failure and a separately labelled post-run analysis are retained.
The [corrected recovery run](../tests/e2e-v2/results/recovery-2026-10-26/matrix-result.json)
passed. Its next downward operation started 120.005 seconds after the prior
completion, exceeding the configured 60-second per-step minimum. Queue-only
recovery without memory data held downward changes; after restart, a fresh
observation window preceded the next downward operation.

The [paired and rolling captures](../tests/e2e-v2/results/paired-and-rolling-2026-10-26/matrix-result.json)
include 210 strict-case broker identity checks and 250 availability samples.
All strict identities and restart counts stayed unchanged. During explicit
rolling, samples showed at least two ready, nonterminating brokers; the largest
combined sample gap was 10.712 seconds. An independent monitor covered the
post-publisher wait because the active harness had loaded the earlier wait code.
This is sampled broker readiness, not proof of uninterrupted client availability.
The corrected harness checks availability first on every wait iteration.

## Final acceptance completed

The [30 October final acceptance](v2.3-acceptance-results.md) supersedes the earlier
release blockers for tasks 6.3/6.4. Eight runtime groups used one immutable image;
31 requirements have named live, controlled or local proof. Astra independently
validated the source/build linkage, raw message IDs and timing with no actionable
findings. The source- and artifact-bound release gate passes.

Independent healthy scale-up confirmation took 90.064 seconds for the CPU-request
cycle, 64.333 seconds for paired in-place changes and 76.181 seconds for explicit
rolling. The latter requires declared startup/readiness/DNS tuning. Original timing
failures remain retained; default Operator settings are not claimed to meet120
seconds. Earlier mutable-tag runs remain historical evidence with their original
provenance limits. The `native` group is this controller's baseline reproduction,
not a new native GKE VPA run.

Other Kubernetes/Operator/RabbitMQ versions remain unverified. Strict rejection of
QoS/restart-required transitions is safe-rejection evidence, not support for those
transitions in place. Full in-place memory-limit changes remain unsupported.
Local acceptance does not establish production compatibility or publish a release.

## Evidence and reproducibility

- [Feasibility probe](../tests/feasibility/README.md) and its checked-in API-only
  captures establish the memory-budget constraint.
- [Actual-controller harness](../tests/e2e-v2/README.md) pins versions, traffic,
  resource profiles and observation rules. Generated runs stay under ignored
  `tests/e2e-v2/evidence/`; reviewed sanitized summaries/captures are retained in
  `tests/e2e-v2/results/` before release claims.
- [Astra review](v2.3-review.md) records source findings and their regressions.
- [Implementation plan](v2.3-implementation-plan.md#acceptance-matrix) lists the
  verification matrix; the final report maps each row to its evidence.

Every runtime result must state its tested image, policy, source timestamps,
resource tuples, broker/container identities, restarts, demand-start/completion
times, message accounting, and any declared capacity block. Missing evidence
remains unverified. Full in-place memory support is not inferred from CPU success.
