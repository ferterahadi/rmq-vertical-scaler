# 2.3 coverage closure results

This report closes specific coverage cases from
[the execution checklist](v2.3-coverage-closure.md). It is separate from the final
release acceptance run. Production compatibility and release readiness are not
inferred from these local results.

## Tested platform

Kubernetes 1.35.0, RabbitMQ Cluster Operator 2.16.1, RabbitMQ 4.4.0-management,
Metrics Server 0.8.0 and cert-manager 1.19.2 ran on one disposable local kind
node (Linux/arm64, 4 CPUs, approximately 6 GiB). Every command used the dedicated
loopback `kind-rmq-v23-closure` context and a separate kubeconfig. The normal
production context was not used for execution.

## Defects discovered and corrected

- Terminal convergence could retain the old UID/container after a replacement
  started directly at the target template. It now records the verified live
  identity and clears obsolete submission/error state only after convergence.
  `TestConvergenceRecordsVerifiedReplacementIdentity` reproduced the old defect.
- The early Infeasible branch skipped current per-broker outcome refresh and
  left the phase as Reconciling. All observed outcomes now refresh before the
  no-write return, and the phase becomes Blocked. A mixed Effective/Infeasible/
  Deferred regression proves target/revision/attempt/timestamp preservation.

Both regressions and the full v2 race suite pass. Astra independently checked
the fixes. Earlier failed harness identity assertions and pre-fix status captures
are retained as historical evidence, not relabelled as corrected results.

## Task 0.3: Operator recovery complete

The [six live Operator cases](v2.3-evidence-bundle.md#browsing-captures) (`tests/e2e-v2/results/closure-operator-2026-10-30/closure-result.json`)
passed against digest `04c17e5cd431ddbd5d03c7431985a28164f0f4b9e1483dc72e12943cb4df2e21`:

- Denying intent persistence prevented broker writes. Denying strategy changes
  retained Prepare; resource updates waited for actual OnDelete.
- Denying resource writes retained the same revision across scaler restart;
  concurrent partial submissions completed after removal without resubmitting
  successful brokers or causing unintended broker restarts.
- A real generated configuration change and an explicit test-supplied checksum
  propagated without replacing brokers under OnDelete. After the deliberate
  deletion, only the intended ordinal changed identity; terminal status matched
  the live UID/container/restart census and did not reuse old submission times.
- A controlled external resource edit caused `ExternalResourceChange`.
  Its tuple stayed in place, the operation retained its original target/revision,
  and attempts/Pod resources/identities remained unchanged during the hold.

All 300 publisher-confirmed IDs were consumed with acknowledgements and zero
duplicates. Actual custom-resource/template/strategy snapshots, operation facts,
generated configuration and IDs are retained with checksums.

An earlier run failed a harness assertion because the Operator aligns whitespace
in generated configuration. The parser now checks the setting/value; its
regression passed. That [failed run](v2.3-evidence-bundle.md#browsing-captures) (`tests/e2e-v2/results/closure-operator-harness-failure-2026-10-30/closure-error.json`)
is preserved, along with [accounting for all 200 confirmed IDs](v2.3-evidence-bundle.md#browsing-captures) (`tests/e2e-v2/results/closure-operator-rescue-2026-10-30/rescue-result.json`)
before fixture recreation. It is not relabelled as a successful full run.
