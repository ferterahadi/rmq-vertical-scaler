# Version-2 scaling policies (2.3.x)

Version 2.3 adds queue/rate and broker CPU/memory policies with explicit paired
requests and limits. New policies start in **`Off`**, which reports recommendations
without changing brokers. Existing environment configurations and unversioned
JSON keep their previous defaults and behavior.

This branch is under verification. Consult the [runtime evidence](v2.3-feasibility.md)
and [runtime results](v2.3-runtime-results.md) before using `Auto`. A successful resize request is not proof of
completion. Infrastructure savings are unmeasured.

## Start with recommendations

From a binary built from this source:

```bash
rmq-vertical-scaler init --config-version 2 --output policy.json
# Edit kubernetes.namespace, kubernetes.rmqServiceName and the resource profiles.
rmq-vertical-scaler generate --config policy.json \
  --image rmq-vertical-scaler:local --output scaler.yaml
kubectl apply -f scaler.yaml
```

Build/load the example `rmq-vertical-scaler:local` image for your cluster, or use
your own tested 2.3 image. Unreleased CLI builds require `--image`; release
binaries pin their matching release image.

The starter enables CPU and memory triggers. It does not require management API
credentials. Queue/rate policies take `RMQ_USER` and `RMQ_PASS` from a Kubernetes
Secret; generation uses the Operator's `<cluster>-default-user` convention.
Do not put credentials into the policy.

Choose a complete starting example:

| Policy | File | Source |
|---|---|---|
| Queue depth / publish rate | [queues.json](../examples/v2/queues.json) | RabbitMQ management API; fresh memory metrics still required to decrease |
| CPU / memory utilization | [resources.json](../examples/v2/resources.json) | Kubernetes Metrics API |
| Both families | [combined.json](../examples/v2/combined.json) | Highest profile recommendation wins |

For Helm, supply the same JSON-shaped object under `policy`:

```bash
helm upgrade --install rvs ./charts/rmq-vertical-scaler \
  --namespace production -f charts/rmq-vertical-scaler/values-v2.example.yaml
```

The example's target namespace must match the release namespace, and its cluster
name must match `serviceName`. Use an image built from this branch until a 2.3
image is published. Setting `policy: {}` is an error; omitted/null `policy` selects
legacy values. Remove customized legacy `profiles`, `debounce`, `checkInterval`,
`scaling`, and `rmq` values when switching to `policy`; inherited defaults are
ignored. New policy fields never become legacy scaling environment variables.

## Profiles and triggers

Every profile declares CPU/memory `requests` and `limits`. `profileOrder` lists
all profiles from floor to ceiling. Each successive profile must increase at
least one value and decrease none; requests must not exceed limits. The scaler
applies a whole profile, never just the field that triggered it.

The examples use a **fixed memory limit** across profiles for strict in-place
operation. CPU limits and CPU/memory requests can still vary. Varying the memory
limit requires the explicitly enabled restart path described below on the tested
platform. The controller does not silently substitute a fixed limit for yours.

Queue/rate triggers look like this inside a complete policy:

```json
{"type":"rabbitmq","metadata":{"mode":"QueueLength","aggregation":"sum","thresholds":{"HIGH":2000}}}
```

- `QueueLength` counts ready **plus unacknowledged** messages. Default `sum`
  counts selected queues once per virtual host/name; `max` selects the deepest.
- `MessageRate` without a selector uses overview cluster ingress publish rate.
  With a selector, it sums queue publish rates. One message routed to three queues
  counts three queue ingress copies; calibrate thresholds for that scope.
- Optional `selector.vhosts` selects exact virtual-host names and
  `selector.queueNameRegex` filters queue names. No filter means all queues visible
  to the API user. Overview rate requires verified global read visibility; when
  that cannot be established, it is unavailable rather than silently changing scope.
- Queue/rate thresholds refer to non-floor profiles, increase with priority, and
  use strict `>` comparison. Empty successful selections mean zero backlog.
  Incomplete pages/statistics are lower bounds that can justify an increase,
  never a decrease. Missing rate fields are unavailable; an empty completed
  selection is a valid zero queue-copy rate.

Utilization triggers follow the KEDA vocabulary:

```json
{"type":"cpu","metricType":"Utilization","aggregation":"max","metadata":{"containerName":"rabbitmq","value":"60"}}
```

Use `type: "memory"` for memory. Omitted targets default to **CPU 60% / memory
75%**. These percentages divide each broker's measured container usage by its
**effective request**, not its limit or requested future allocation. CPU and memory
select their busiest broker independently; the maxima can come from different
brokers. Measured utilization can exceed 100%. Only the RabbitMQ container is resized.

## Timing and missing data

| Setting | Default | Meaning |
|---|---|---|
| `pollingInterval` | 15 seconds | Observation cadence |
| `behavior.scaleUp.stabilizationSeconds` | 30 seconds | Sustained demand before a direct jump upward |
| `behavior.scaleDown.stepIntervalSeconds` | 300 seconds | Full observation interval for each single downward step; minimum 60 |
| `behavior.scaleDown.memoryHeadroomPercent` | 20 | Peak working set must fit below 80% of the candidate memory limit |
| `behavior.metrics.maxAgeSeconds` | 60 seconds | Maximum resource-sample age, using source timestamps |

Available valid demand can justify increases during another source failure.
Every enabled signal must permit a reduction, and every broker needs fresh
memory observations even for queue-only policies. Repeated cached timestamps do
not fill a window. A restart, broker replacement, failed critical observation,
or policy change discards observation eligibility.

The healthy scale-up objective is confirmed effective resources across all
brokers within 120 seconds of first observed sustained demand, including default
stabilization. The implementation records deadline misses. Capacity problems,
explicit rolling, and user timings require separate interpretation; they do not
turn an accepted patch into a successful or timely resize. A four-profile ladder
needs at least 15 minutes to descend three default steps, excluding resize time.

## In-place and explicit rolling

```json
"updatePolicy": {"mode":"Auto","allowRollingFallback":false}
```

`Auto` authorizes resource changes. The default strict path submits in-place
requests across all brokers concurrently. It first observes the owned
StatefulSet using `OnDelete`, synchronizes the cluster resource/template, then
checks effective resources, current generations, readiness, and resize conditions.
The `OnDelete` override also affects later Operator upgrades; coordinate those
operations. One installation and one scaler replica per target are required.

On tested Kubernetes 1.35 / Operator 2.16.1 / RabbitMQ 4.4.0, changing a memory
limit in place leaves the running RabbitMQ memory budget stale. Strict mode
therefore reports **`MemoryLimitRequiresBrokerBudgetReload` before resource or
strategy writes**. Removing watermark triggers does not remove this broker
behavior. See the [measured report](v2.3-feasibility.md).

Set `allowRollingFallback: true` only when broker restarts are acceptable. The
controller keeps the full target profile and delegates rolling to the Operator's
StatefulSet path. It requires at least three ready brokers and the Operator's
quorum-aware shutdown hook; a PodDisruptionBudget alone does not govern StatefulSet
rolling replacements. Availability, timing, and restart behavior are separate
from strict in-place evidence. The scaler does not execute broker commands or
change memory watermark configuration.

Rolling latency also depends on broker startup and DNS settings. The default
Operator startup delay did not meet the 120-second objective. See the
[explicit low-latency deployment and measured failures](v2.3-rolling-latency.md)
before relying on that objective for rolling fallback.

Partial/deferred work retains its target and successful changes. The controller
reconciles remaining brokers and never automatically rolls them back. An upward
committed operation may finish after demand falls; a later reduction still needs
its full window. After restart, incomplete decreases rebuild a separate safety
window while the operation remains unresolved. Unexplained pending/mixed state
without operation facts, incompatible policy changes, and external resource edits
are blocked for inspection.

## Inspect and migrate

```bash
kubectl logs -f deployment/rmq-vertical-scaler -n production
kubectl get configmap rmq-vertical-scaler-status -n production \
  -o jsonpath='{.data.status\.json}'
```

Status separates recommendation, active operation, per-broker desired/effective
resources, missing data, blockers, and a bounded last-operation summary. Operation
facts survive restarts; samples/timers do not. Helm manages the read-only policy
ConfigMap and its checksum, while the controller creates its own status ConfigMap.
Do not replace runtime status with an empty template during upgrades.

To migrate, declare profiles matching actual requests **and limits**, deploy
`Off`, inspect recommendations and metric completeness, then enable `Auto` after
checking platform constraints. Do not run old and new scalers against the same
cluster. The scaler Deployment uses `Recreate` to avoid rollout overlap; this is
not distributed locking against duplicate installations or external writers.
Missing/invalid `run --config` input is fatal and never falls back to legacy Auto.
