# 2.3 feasibility: broker memory limits

The tested platform applies CPU/memory requests and limits in place, but the
running RabbitMQ memory budget does not follow those limit changes. The full
memory-resize feasibility gate fails. The opt-in 2.3 controller is under verification and blocks those transitions in
strict mode. The legacy controller is unchanged by this probe.

## Measured behavior

On 26 October 2026, a disposable local kind cluster ran three persistent,
Operator-managed RabbitMQ brokers. Each transition updated the custom resource,
waited for the generated StatefulSet template, then submitted all three Pod
resize requests concurrently. The actual StatefulSet was observed using
`OnDelete` before resource edits. No broker reconfiguration or restart was used.

All three brokers reported the same results:

| Observation | Baseline | Increase | Decrease |
|---|---|---|---|
| CPU request / limit | 100m / 1 | 200m / 1500m | 100m / 1 |
| Memory request / limit | 256 MiB / 1024 MiB | 512 MiB / 1536 MiB | 256 MiB / 384 MiB |
| Operator ConfigMap memory override, bytes | 858,993,460 | 1,288,490,189 | 322,122,548 |
| Running container's mounted override, bytes | 858,993,460 | 858,993,460 | 858,993,460 |
| Running broker memory alarm threshold, bytes | 515,396,076 | 515,396,076 | 515,396,076 |
| Container restarts | 0 | 0 | 0 |

Kubernetes effective container status, observed Pod generations, readiness, and
absence of pending/in-progress resize conditions confirmed both resource changes.
Pod UIDs and container IDs stayed unchanged. The clean repeat also compares
actual cgroup v2 CPU quotas and memory limits with the expected values, and waits
at least 60 seconds after each transition before recording the broker budget.

The final running alarm threshold is approximately **491.52 MiB**, above the
**384 MiB** container limit. Before decreasing, the probe required fresh Metrics
API observations and 20% headroom under that smaller limit. In the clean repeat,
the five pre-decrease samples peaked at 179,195,904 bytes (170.89 MiB); five
post-decrease samples peaked at 276,709,376 bytes (263.89 MiB). Idle working set
fits that guard; the broker's stale alarm threshold still does not. This shows
why a working-set guard alone is insufficient. No out-of-memory event or message
loss was induced or measured.

| Runtime | containerd 2.2.0, cgroup v2, Linux/arm64 |
| RabbitMQ Cluster Operator | 2.16.1 |
| RabbitMQ | 4.4.0-management; image digest recorded in each snapshot |

Setting a quorum queue default does not prove quorum replication, message
safety, or availability under load. This test uses idle brokers to isolate the
budget behavior. It does not meet the full three-broker 2.3 release gate or
establish the two-minute scale-up objective.

## Why the values diverge

The Operator's generated ConfigMap changes with the memory limit. Its
`userDefinedConfiguration.conf` is mounted into the container using `subPath`;
the existing mounted file remains at its initial value. The running broker's
reported alarm threshold also stays unchanged. This is observed behavior on
the pinned versions above, not a claim that every RabbitMQ deployment behaves
identically. See the Operator's pinned
[configuration builder](https://github.com/rabbitmq/cluster-operator/blob/v2.16.1/internal/resource/configmap.go)
and [StatefulSet builder](https://github.com/rabbitmq/cluster-operator/blob/v2.16.1/internal/resource/statefulset.go).

Removing watermark-based scaling signals does not remove RabbitMQ's own memory
alarm mechanism. Raising a hard limit with an unchanged broker budget can leave
new capacity unused by that mechanism; reducing it below the stale threshold
removes the intended alarm headroom. The latter risk is inferred from the
measured threshold/limit mismatch, not a demonstrated failure under traffic.

## Consequence for implementation

Phase 0 of the [implementation plan](v2.3-implementation-plan.md#4-phase-0-feasibility-gate)
requires reporting this constraint before building the new automatic resize
path. It explicitly disallows hidden broker commands, silently enabling rolling
restarts, and describing requests-only work as full memory-limit scaling.

The existing design already permits explicitly configured rolling fallback.
Two potential paths require distinguishing:

- A fixed, explicitly declared memory ceiling allows paired CPU/memory requests
  and CPU limits to change without changing the broker's memory budget. It gives
  up elastic memory hard limits; it does not establish the originally proposed
  full memory-limit cycle.
- Changing the memory ceiling through an explicitly enabled Operator rolling
  update reloads startup configuration. Strict in-place mode must remain blocked
  for that transition. Restart availability, quorum behavior, convergence,
  recovery, and the two-minute timing objective require separate validation.

Neither is silently selected by this probe. A supported dynamic budget-update
mechanism would be a separate design change with additional privileges and
failure ordering; it is not implemented here.

## Reproduce and inspect

The [probe instructions](../tests/feasibility/README.md) pin setup versions and
explain exit codes, safety bounds, artifacts, and cleanup. Generated captures
remain under the ignored `tests/feasibility/evidence/` directory; reviewed,
sanitized captures are retained under `tests/feasibility/results/`.

The [clean repeat captures](v2.3-evidence-bundle.md#browsing-captures) (`tests/feasibility/results/kind-1.35-operator-2.16.1-rabbitmq-4.4.0`)
include baseline/increased/decreased snapshots, source metrics, platform details,
concurrent submission times, a failed-gate result, and SHA-256 checksums. The
cycle ran between 07:51 and 07:53 UTC. An earlier independent run produced the
same budget mismatch; its generated output remains ignored locally.

The harness uses read-only broker diagnostics. It does not grant `pods/exec` to
the scaler, install a new controller, or change the normal kubeconfig context.

## API-only confirmation

At the user's request, the current harness reads the running threshold from
`GET /api/nodes` field `mem_limit`. It executes no Erlang or broker commands.
`mem_used` reports broker memory usage; it is distinct from the Kubernetes
container working set used by the scaling policy. `mem_limit` is a broker alarm
threshold, not the container hard limit. See the [RabbitMQ monitoring reference](https://www.rabbitmq.com/docs/monitoring#node-metrics).

A fresh [API-only cycle](v2.3-evidence-bundle.md#browsing-captures) (`tests/feasibility/results/api-only-kind-1.35-operator-2.16.1-rabbitmq-4.4.0`)
on 26October2026 between08:35 and08:38UTC reproduced the same failure. Expected
overrides are independently calculated as `limit - min(limit div5, 2GiB)` for
Operator2.16.1. The pinned 64-bit fixture explicitly uses relative0.6; expected
thresholds are515396076,773094113,193273528bytes. Actual API thresholds remain
515396076bytes at every stage. The assertion checks exact expected values, not
merely movement in the correct direction. This avoids requiring runtime Erlang
evaluation. It is a fixture-specific expectation, not a universal API for reading
all internal memory-budget inputs.

The earlier captures retain historical mounted-file and cgroup diagnostics. The
API-only harness instead verifies Kubernetes effective status and the management
API threshold; it does not claim to reread kernel files. Both results remain
platform feasibility evidence, not full controller acceptance.
