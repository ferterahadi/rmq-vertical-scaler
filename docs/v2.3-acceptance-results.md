# Final 2.3 acceptance — 30 October 2026

The final immutable build passed the documented local acceptance matrix: 31
requirements, supported by eight runtime groups and controlled/local regressions.
Astra independently checked the retained results, source/build linkage, message
IDs and timing, with no actionable findings. This is local acceptance, not a
production compatibility claim or a published release.

## Tested build and platform

- Version 2.3.0, Linux/arm64 image
  `sha256:5bec6039f6cd43dc829f2141007a113af5487fa61b6782fb824a905bca41a2b9`.
  Every policy installation verified its runtime image identity. All 28 production
  inputs and the binary's exact bytes are linked to retained OCI metadata.
- Three Operator-managed RabbitMQ brokers with persistent storage on disposable
  kind: Kubernetes 1.35.0, Cluster Operator 2.16.1, RabbitMQ 4.4.0-management,
  Metrics Server 0.8.0 and cert-manager 1.19.2; four CPUs and about 6 GiB RAM.
  Metrics Server used a test-only insecure kubelet TLS option.
- The [tracked coverage summary](../tests/e2e-v2/acceptance-summary.json) names
  each requirement's live, controlled or local evidence. These are 31 covered
  requirements, not 31 independent live scenarios. Other platform versions remain
  unverified.

## Scale-up timing

These independent times include stabilization, polling, reconciliation and the
first observation of completion. Each satisfied the 120-second healthy-capacity
objective, with no controller-recorded deadline miss.

| Final-image scenario | Independent completion |
|---|---:|
| Two-profile CPU-request cycle, 100m → 800m | 90.064 seconds |
| Paired requests and CPU limit, strict in-place | 64.333 seconds |
| Explicit full-memory rolling fallback | 76.181 seconds |

**Rolling requires explicit startup, readiness and DNS tuning.** The default
Operator diagnostic still failed at 210.0 seconds; removing its startup delay
alone still failed at 121.1 seconds. The final run retained normal quorum-aware
shutdown guards and sequential Operator replacement. The scaler does not apply
the deployment tuning. See [rolling prerequisites and failed diagnostics](v2.3-rolling-latency.md).

The runtime group named `native` runs this project's controller with the
two-profile baseline policy. It is not a new GKE VPA run or a matched VPA
performance comparison. The original [GKE experiment](usage.md#experiment-evidence)
remains separate.

## Runtime results

| Group | Verified result |
|---|---|
| CPU cycle | Default-duration load and down observation; 20,167 confirmed IDs consumed, zero duplicates, no broker replacement or restart |
| Recovery | Seven cases covering Off signal families, missing metrics, partial changes, supersession and restart; 2,600 IDs consumed once; fresh downward observation/step intervals enforced |
| Deferred | Actual kubelet Deferred under declared capacity pressure; retained target and successful attempts; same operation converged after filler removal; 100 IDs consumed once |
| Paired and rolling | Strict paired changes, memory-limit rejection before writes, explicit rolling up/down with exact broker-budget readback; 12,614 IDs consumed once |
| API scope | Admin/restricted queue visibility and cluster ingress versus selected queue copies; exact durable-ID accounting |
| Platform | QoS, RestartContainer and actual Infeasible cases safely blocked; 50 IDs consumed once in each case |
| Operator recovery | Six interruption, replacement and external-drift cases; retained targets/attempts and correct terminal identities; 300 IDs consumed once |
| Pagination | Two real API pages, 502 selected queues, sum 37/max 20; all 37 IDs consumed once; provider values/timestamps/windows matched all three current broker containers |

The rolling group included one uncertain publish retry. Zero observed duplicate
IDs does not establish exactly-once delivery. Broker availability was sampled:
62 observations, at least two ready nonterminating brokers, maximum gap 33.302
seconds. This does not prove uninterrupted client availability.

Four supplementary live checks independently recomputed CPU-only, memory-only,
paired and combined queue/resource recommendations. They used low test thresholds
in `Off`, verified no resource/strategy/identity changes, and do not claim an
automatic CPU-pressure load test. Controlled regressions cover exact filtered-rate
arithmetic, stale/partial sources, jitter and lost resize replies. The full Go race
suite, vet, tidy-diff, Helm checks, 33 harness/gate tests and 12 feasibility tests passed.

Strict in-place memory-limit changes remain unsupported on this platform.
Rejection before writes and explicitly enabled rolling are the accepted behaviors.
