# Rolling resize latency

The 120-second scale-up objective includes the default 30-second stabilization
and 15-second polling. Explicit rolling also includes three sequential broker
replacements. It requires a deployment with enough capacity and startup latency
that fits the remaining budget; enabling fallback alone cannot guarantee it.

## Why the default fixture missed

Operator 2.16.1 inserts a 30-second setup-container sleep by default, before each
broker boots. The three sleeps alone consume about 90 seconds. Actual default
rolling diagnostics took 208.3 seconds by controller timestamps and 210.0 seconds
by independent confirmation. The earlier 195-second result remains a failure.

Changing only the startup delay to zero reached 119.1 seconds in status, but
independent confirmation took 121.1 seconds. It also failed. The harness now
rejects either a recorded deadline miss or independent confirmation after 120
seconds, in both standalone and matrix rolling runs.

## Explicit low-latency deployment

The tested local deployment used these RabbitmqCluster settings:

```yaml
spec:
  replicas: 3
  delayStartSeconds: 0
  override:
    statefulSet:
      spec:
        template:
          spec:
            containers:
            - name: rabbitmq
              readinessProbe:
                tcpSocket:
                  port: 5672
                initialDelaySeconds: 1
                periodSeconds: 2
                timeoutSeconds: 5
                successThreshold: 1
                failureThreshold: 3
```

This example uses the tested plaintext AMQP port. Keep your deployment's
existing probe handler and port, including TLS settings, when changing its cadence.
The readiness predicate remains the Operator's AMQP TCP check, sampled more
frequently. The normal quorum-aware preStop hook remains intact. No shutdown
check is skipped, no brokers are deleted concurrently, and stabilization is
not shortened. The scaler does not apply these startup/probe settings for you.

Zero delay also requires timely DNS. In the disposable kind cluster, CoreDNS's
Kubernetes TTL and cache cap were set to five seconds, with success/denial
caching disabled for cluster.local. CoreDNS Pods were restarted and observed
ready. The headless service published not-ready addresses. A separate DNS
observer resolved the replacement broker addresses during the rollout.

Operator's [pinned API contract](https://github.com/rabbitmq/cluster-operator/blob/v2.16.1/api/v1beta1/rabbitmqcluster_types.go#L89-L98)
permits reducing the delay when DNS caching/publication supports it. Configure
and verify your own cluster's DNS before using zero delay; this local result
is not a default-Operator or production latency guarantee.

The revised diagnostic reached 104.0 seconds in status and 104.5 seconds by
independent confirmation, with all 100 confirmed IDs consumed once. The
[retained diagnostics](../tests/e2e-v2/results/rolling-latency-diagnostics-2026-10-30/summary.json)
include init timestamps, DNS configuration, endpoint observations, message IDs
and every failed attempt. The [final immutable-build acceptance](v2.3-acceptance-results.md)
repeated this configured path at 74.571 seconds in status and 76.181 seconds by
independent confirmation. Capacity and DNS prerequisites were recorded before
demand. Sampled broker readiness remained at least two; this is not continuous
client-availability proof.
