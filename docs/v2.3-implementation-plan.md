# Version 2.3 implementation plan

Status: implementation and local acceptance complete, 30 October 2026.
Full in-place memory-limit changes remain unsupported on the tested platform;
strict rejection and explicit rolling passed. Shipping remains separate. See
the [final acceptance receipt](v2.3-acceptance-results.md).

The [measured feasibility report](v2.3-feasibility.md) records a three-broker
Kubernetes 1.35 / Operator 2.16.1 / RabbitMQ 4.4.0 cycle: effective requests and
limits changed without restarts, but the running broker memory budget stayed
fixed. After reduction, its alarm threshold exceeded the container limit.
Do not treat successful Kubernetes resizing as permission to bypass this gate.
The implementation continues under the already agreed strict-block/explicit-fallback
policy: strict mode blocks memory-limit transitions before writes. It does not
silently alter profile limits. Full in-place memory support remains failed;
rolling and release claims need their own evidence. Checklist completion follows
verified outputs, not the presence of code alone.

Build an independent RabbitMQ vertical scaler with KEDA-style trigger configuration
and VPA-style separation between recommendations and updates. Preserve existing
configurations. Prove that resource changes reach every broker; an accepted API
patch is not a completed resize.

This is an engineering plan. The [README](../README.md) stays focused on current
user-facing behavior and setup. The contracts below guide the opt-in source implementation; checked work has
local evidence. Use the policy guide for user instructions and the runtime report
for verification boundaries. This plan is not a release receipt.

## 1. Purpose and evidence

The [native GKE VPA experiment](vpa-experiment-evidence.md#native-vpa-observation)
tested a fixed-policy CPU-request cycle of 100m → 800m → 100m over 15 minutes,
with five minutes of real traffic followed by cooldown. The recommendation
reached 800m, but applied requests remained 100m in all 171 samples; the audit
recorded no Pod resize calls. A [separate fast custom recommender](vpa-experiment-evidence.md#separate-custom-recommender-observation)
completed that cycle through GKE's updater with zero broker restarts.

These results establish a responsiveness requirement, not StatefulSet
incompatibility or proof that native VPA never works. Neither experiment ran
this repository's controller or the RabbitMQ Cluster Operator. The custom
recommender result must not be attributed to this scaler. Only CPU requests
changed; throughput benefits, memory resizing, message safety, and infrastructure
savings were not established. Cost and new-controller response times are unmeasured.

Version 2.3 must demonstrate controlled resource allocation under load and safe
resource reclamation, with explicit evidence of desired versus effective resources.

## 2. Agreed requirements

| Area | Required behavior |
|---|---|
| Controller | Keep our own scaler; no dependency on KEDA or GKE VPA controllers. |
| Configuration | Extend JSON and Helm; do not introduce a scaler custom resource definition. |
| Profiles | Keep CPU and memory paired; explicitly declare requests and limits in every new-format profile. |
| Trigger families | Queue depth/publish rate and CPU/memory utilization; either family or both. No broker memory-watermark trigger. |
| Combining triggers | Highest profile recommendation wins; every enabled signal must permit a reduction. |
| Queue scope | All queues visible to the API user by default; optional virtual-host and queue filters apply to queue/rate signals. |
| Queue depth | Default to total messages across selected queues, including ready and unacknowledged messages; allow explicit maximum-depth aggregation. |
| Utilization | Size for the busiest broker per resource; CPU and memory maxima may come from different brokers. Measure against effective requests. |
| CPU target | 60% by default, configurable. |
| Memory target | 75% by default, configurable. |
| Polling | 15 seconds by default, configurable. |
| Update policy | New format defaults to recommendation-only `Off`; explicit `Auto` enables changes. |
| Resize policy | Require in-place resizing by default; rolling fallback must be explicitly enabled. |
| Direction | Jump directly to a justified higher profile; reduce one profile step at a time. |
| Broker concurrency | Submit each in-place profile change across all brokers concurrently; do not wait for one broker to finish before submitting to another. |
| Up stabilization | 30 seconds by default, configurable. |
| Up completion objective | Effective resources confirmed across all brokers within 120 seconds of first observed sustained overload, including stabilization, on a healthy cluster with capacity. |
| Down timing | Five minutes per step by default, configurable; reject values below 60 seconds. |
| Memory reduction guard | Require 20% headroom below the proposed memory limit by default, configurable, using peak observed memory over the down-step window. |
| Metric freshness | Maximum resource-sample age 60 seconds by default, configurable; use source timestamps. |
| Partial metric failure | Available valid signals may justify scale-up; missing/stale enabled signals block scale-down. With all signals unavailable, hold and report. |
| Queue-only dependency | Queue-only operation can run without resource metrics; downward profile changes require fresh memory observations. |
| Partial resize | Keep the target and successful changes; reconcile incomplete brokers. Do not automatically roll back. |
| Changing demand | A higher recommendation may supersede an unfinished target; do not begin downward transitions while a resize is unresolved. |
| Restart | Restart observations and stabilization timers. Inspect existing operations immediately; new writes require rebuilt policy checks. |
| Reporting | Structured logs plus a status ConfigMap; expose recommendations, desired/effective resources, freshness, and blocked reasons. |
| Deployment | One instance and one installation per target; scaler Deployment uses `Recreate`. No leader election or standby replicas. |
| Compatibility | Preserve legacy configuration semantics and defaults. New behavior requires an explicit new-format configuration. |
| Release gate | Operator-managed three-broker integration tests under load/cooldown, including CPU/memory requests and limits and failure recovery. |

The following sections choose implementation details such as field names,
module boundaries, and retry behavior. They do not add new product modes.
They are engineering conventions to validate, not additional interview decisions.
In particular, conservative handling of unknown resources must not disable
otherwise safe queue-driven increases merely because resource metrics are absent.

### Version constraint already established

Kubernetes 1.33 documents that reducing a memory limit requires
`RestartContainer`; it cannot provide the agreed restart-free full memory cycle.
Kubernetes 1.34 documents best-effort memory-limit reduction with `NotRequired`.
Therefore, full in-place request-and-limit scale-down requires a validated
1.34-or-newer platform, not the current request-only feature's 1.33 assumption.
See [1.33 limitations](https://v1-33.docs.kubernetes.io/docs/tasks/configure-pod-container/resize-container-resources/#limitations)
and [1.34 limitations](https://v1-34.docs.kubernetes.io/docs/tasks/configure-pod-container/resize-container-resources/#limitations).

Do not silently enable rolling fallback or a restart-required container policy
to satisfy a test. Unsupported operations stay blocked unless rolling fallback
was explicitly configured. Legacy request-only support remains separate.

The Operator generates a memory override, and RabbitMQ can determine relative
memory thresholds at startup or when explicitly updated. Verify the deployed
versions rather than assuming that changing a cgroup limit updates the broker's
own budget. Sources: [Operator memory configuration](https://www.rabbitmq.com/kubernetes/operator/using-operator#resource-requirements)
and [RabbitMQ memory thresholds](https://www.rabbitmq.com/docs/memory).

**Exit:** a recorded compatibility matrix and a proven supported path for
changing both requests and limits without restarts. If the broker budget cannot
remain correct under that path, report the design constraint before proceeding;
do not add hidden broker commands or claim request-only scaling meets the plan.
The matrix must identify control-plane/kubelet/runtime, Operator and RabbitMQ
versions, QoS class, container resize policies, and all four resource values
tested in both directions. Keep unsupported and untested cells explicit. Read-only broker
diagnostics used by the test harness do not justify adding `pods/exec` to the
scaler or dynamically reconfiguring brokers.

### Proposed JSON contract

Profile resource values below are illustrative, not calibrated production sizes.
`profileOrder` makes priority explicit instead of relying on JSON object order.
The first entry is the floor. All settings shown are new-format settings.

```json
{
  "configVersion": 2,
  "profileOrder": ["LOW", "MEDIUM", "HIGH", "CRITICAL"],
  "profiles": {
    "LOW": {
      "requests": { "cpu": "330m", "memory": "2Gi" },
      "limits": { "cpu": "660m", "memory": "4Gi" }
    },
    "MEDIUM": {
      "requests": { "cpu": "800m", "memory": "3Gi" },
      "limits": { "cpu": "1600m", "memory": "6Gi" }
    },

      "limits": { "cpu": "3200m", "memory": "8Gi" }
    },
    "CRITICAL": {

  "rmq": { "host": "rabbitmq.production.svc.cluster.local", "port": "15672" }

```

For queue/rate only, remove the CPU/memory trigger entries. For utilization only,
keep just CPU/memory entries and omit the RabbitMQ management connection.
Do not require management API readiness or credentials when no queue/rate trigger
uses it. CPU and memory triggers may be independently enabled; resource changes
still apply one paired profile.

Optional RabbitMQ trigger metadata: `selector.vhosts` is an exact-name list and
`selector.queueNameRegex` is a Go-compatible regular expression. Omitted filters
mean all visible queues. QueueLength supports `sum` (default) and `max`.
CPU/memory aggregation is `max`; the agreed design does not expose an average mode.

The trigger vocabulary follows [KEDA CPU](https://keda.sh/docs/2.18/scalers/cpu/)
and [KEDA memory](https://keda.sh/docs/2.18/scalers/memory/) conventions. Busiest-broker
aggregation and paired vertical profiles are this scaler's own policy.

### Validation rules

- Every ordered profile appears exactly once, has all four positive quantities,
  and satisfies request ≤ limit. Require exact equality between the profile-name
  set and `profileOrder`; reject duplicate names/JSON keys and unused profiles.
  Quantities are compared numerically, including Kubernetes CPU precision rules.
- Profile tuples are nondecreasing in order; adjacent profiles must differ.
  Never allow a nominal upward step to secretly lower another resource.
- Validate proposed profiles against the current Pod-wide QoS class before
  writes, including other containers. Do not change QoS through a resize.
- Require at least one supported trigger, valid target percentages, positive
  polling/freshness values, and nonnegative integer stabilization values. Down-step interval is
  at least 60 seconds; memory headroom is in the range 0 to less than 100%.
  Utilization targets are positive finite percentages; requests are reservations,
  so measured utilization may exceed 100%. Do not clamp measured values to 100%.
- Queue/rate thresholds refer to existing non-floor profiles, are positive,
  and increase with profile priority. Use the existing strict `>` comparison
  for queue/rate thresholds. Reject unknown keys and invalid selectors.
- A missing CPU/memory `value` receives its agreed default; `Utilization`
  values are numeric percentage strings validated before normalization. Resource
  triggers must target the RabbitMQ container, not a sidecar whose resources
  this controller does not resize.
- `Off` and `Auto` govern whether to apply. `allowRollingFallback` independently
  authorizes a restart path; `Auto` does not imply fallback.
  Reject string booleans and unknown/case-mismatched enum values. Validate all
  policy durations as integer seconds and bound arithmetic/storage safely.

**Exit:** all three trigger combinations validate, CLI errors identify field
paths, malformed new configs never become legacy defaults, and existing fixtures
and env loading remain compatible.

Build the broker census from the target `RabbitmqCluster` UID, its owned
StatefulSet UID and replica count, and each owned Pod/ordinal. Check controller

or replaced containers, replica-count disagreement, and unreadable ownership are

Do not resize a similarly labelled unrelated Pod. Membership changes invalidate
down windows and require a fresh census; this scaler does not change replicas.

### Metric meanings

| Signal | Source and interpretation |
|---|---|
| Total queue messages | Sum selected queues' `messages` once per `(vhost, name)`, including ready plus unacknowledged messages and excluding quorum-replica copies. Use the queue list consistently; overview totals are diagnostic. |
| Maximum queue depth | Largest `messages` value among selected queues. |
| Publish rate | No selector: overview publish rate, only where Phase 0 proves its visibility matches all queues visible to this API user. With a selector: sum selected queues' publish rates. These are different counting scopes; report which is used and never switch sources silently after an error. |
| CPU utilization | Average CPU usage from the resource sample divided by that broker's effective CPU request. |
| Memory utilization | Container working-set bytes divided by that broker's effective memory request. |
| Memory safety guard | Peak observed working set across the complete down-step window compared with the proposed limit, independently of whether a memory trigger is enabled. |

Use complete pagination for selected queues. Failed pages are an incomplete
signal, not a smaller backlog. Deduplicate by `(vhost, name)` and detect pagination
churn; incomplete nonnegative queue sums/maxima are lower bounds that can justify
an increase, never a reduction. The same rule applies to partial broker metrics.
An empty successful selection is zero backlog
in the new engine; a newly created/idle broker's missing rate fields require an
explicit tested idle-versus-unavailable rule. Preserve legacy empty-list behavior.

For example, one message published to an exchange and routed to three selected
queues contributes one ingress publish but three queue ingress copies. Adding
a queue filter therefore requires deliberately calibrated rate thresholds;
matching every queue with a regex still selects queue-copy semantics. Test
fan-out, unroutable messages, repeated queue names across vhosts, and restricted
API users. If overview scope cannot be established for a user, mark that signal
unavailable; do not silently count inaccessible queues or substitute a different
rate definition. Reference: [RabbitMQ HTTP API](https://www.rabbitmq.com/docs/http-api-reference).

Resource freshness uses `PodMetrics.timestamp`, with the CPU sample's `window`
retained. Repeated timestamps do not create additional observations. Reject
samples predating the current container, invalid windows, or unexplained future
timestamps. Resource samples at different broker timestamps remain separate.
An averaging window overlapping a resource change cannot alone justify a
reduction; rebuild adequate post-convergence observations first.
Record HTTP-observed timestamps separately for management snapshots; do not
claim that receipt time proves the age of RabbitMQ's internal statistics.
Use per-source fetch deadlines shorter than a poll interval; a failed source
must not serialize/block the other sources. Retain the last value for diagnostics
but mark a failed collection incomplete for downscale decisions. Reusing a fresh
resource sample is allowed only within its age bound; it does not add an
independent sample or extend the covered down-window endpoint. A down window
requires distinct samples spanning the interval for every broker, no stale gaps,
and a fresh final collection; an identical timestamp alone cannot fill a window.

CPU is a windowed usage measurement; memory is a working-set measurement, not
physical allocation or a guarantee against OOM. Source:
[Kubernetes resource metrics](https://kubernetes.io/docs/tasks/debug/debug-cluster/resource-metrics-pipeline/).

**Exit:** zero, empty, stale, duplicate, missing, replaced-broker, and partial
observations are distinguishable. Missing brokers or unknown effective resources
never become zero usage or proof of convergence.

### Profile selection

For each enabled resource trigger, calculate the required request from measured
usage and its target. CPU uses the maximum CPU requirement over brokers; memory
uses the maximum memory requirement. They need not identify the same broker.

```text
requiredCPU    = max(broker CPU usage / 0.60)
requiredMemory = max(broker working set / 0.75)
resourceProfile = smallest profile satisfying enabled resource requirements
recommendation  = highest(resourceProfile, queueProfile, rateProfile)
```

Use configured targets in code, with careful unit conversion and conservative
rounding. Project usage against each candidate's requests rather than stepping
up/down from current utilization alone; otherwise increasing the denominator
could immediately create a false recommendation to shrink.

If demand exceeds the ceiling, recommend the highest profile and explicitly
report insufficient configured capacity. Reaching that profile does not mean
the utilization target was met. Do not resize beyond declared profiles.

### Timing and reductions

1. Track how long demand justifies at least a candidate higher profile. A still
   higher recommendation must not continually reset the timer for the lower
   sufficient candidate. Keep one `since` value per profile boundary; clear it
   when valid evidence no longer supports that boundary. For example, alternating
   MEDIUM/HIGH demand for 30 seconds qualifies MEDIUM; HIGH needs its own sustained
   evidence. Jump to the highest currently qualified profile. Missing all usable
   evidence interrupts continuity; another valid signal can maintain it.
   Reset all observation timers on process restart.
2. Allow an upward jump after the configured stabilization period. Valid signals
   can justify it despite another signal being unavailable. When no signal is
   usable, hold and report.
3. Start a down-step observation window only after the current operation is
   confirmed complete. Require all enabled signals to permit the immediately
   lower profile throughout that window and require fresh memory observations
   for every broker. Missing data invalidates downscale eligibility; require a
   complete replacement window before reducing resources. At startup with no
   operation, a verified common effective profile starts this window. Reset it
   on higher demand, unsafe memory, membership change, or incomplete observations;
   a low instantaneous recommendation is not a completed window.
4. Require `peakMemory <= candidateMemoryLimit * (1 - headroomPercent / 100)`
   for each broker. Check a fresh sample again before submission. Do not use
   another broker's larger memory margin to offset an overloaded broker.
5. Submit the one-step change across brokers concurrently. Start the next window
   after all brokers converge, not at patch acceptance.

For a proposed 6Gi limit and the default 20% margin, the observed peak must be
at most 4.8Gi. This guard reduces risk, but cannot eliminate memory spikes or
prove that the broker's internal memory budget is appropriate; Phase 0 addresses
that separate requirement.

If initial/manual resources do not match a profile, compare actual resource
tuples. Any resource decrease must pass reduction guards even if CPU increases.
Do not derive direction or current state solely from a CPU string. Use these
conservative initialization rules rather than inventing a current profile:

- A durable operation explains a mixed cluster: reconcile that recorded target
  using the recovery rules below. Do not select another downward step.
- Without an operation, a demand-justified profile may increase resources only
  if it dominates every broker's known desired and effective tuple. This remains
  possible with queue signals when utilization metrics are unavailable.
- If tuples are unknown or a mixed/off-profile cluster would require a decrease,
  report `Unknown`/`Mixed`/`Unmapped` and block that write. Establish a known common
  configured profile through an explicit configuration/migration action first;
  do not round CPU to a profile or silently round resources down. Resources
  above the configured ceiling require this same treatment, not forced clamping.

The last rule is an implementation safety convention for unmanaged initial
state, not an additional scaling mode. It does not prevent retrying a known
partially submitted operation or reporting a recommendation.

**Exit:** fake-clock tests prove stable decisions, no denominator oscillation,
freshness/headroom enforcement, reset behavior, and missing-metric asymmetry.

### Control flow

```text
[Observe sources] -> [Recommend profile] -> [Check policy]
                                             |
                              Off: report only / Auto: persist intent
                                             |
                              [Submit all brokers] -> [Observe convergence]
```

For an eligible new operation:

1. Persist intent before broker writes. If durable state cannot be saved, report
   the failure and do not begin a new mutation.
2. Confirm in-place capability, permission, current QoS, and compatible container
   resize policies. Set and verify the Operator's `OnDelete` override before
   updating its resource template: wait until the owned StatefulSet itself shows
   `OnDelete`. Do not overwrite unrelated overrides or directly take ownership
   of Operator-managed StatefulSet fields. Do not change `resizePolicy` to make
   a restart-capable container pass in-place preflight.
3. Synchronize all four desired resource values to `RabbitmqCluster`, then
   wait for the owned StatefulSet template to reflect that tuple under
   `OnDelete`, then reconcile its pods against the same durable target. Recover
   controller-created custom-resource/Pod drift on subsequent passes instead
   of inferring completion from custom-resource CPU. This order makes any broker
   replacement inherit the intended resources; the wait counts toward latency.
4. Submit changed requests and limits together per pod, concurrently across
   brokers, using `pods/resize`. Do not wait for one broker's completion before
   sending another broker's request. Skip pods already requesting the target;
   observe them instead of continually resubmitting identical patches. Launch
   all three broker requests in the same fan-out round, with independent bounded
   request contexts; slow responses must not serialize the remaining submissions.
   Use UID/resource-version preconditions and re-read after conflicts. Preserve
   sidecars and all unrelated resource fields.
5. Confirm every expected broker's effective tuple, container identity/readiness,
   relevant generation, and active resize conditions. Also confirm the Operator's
   generated resource template matches the target before declaring convergence.

Kubernetes exposes effective resources in
`status.containerStatuses[*].resources`; Pod spec is desired state. Pending or
in-progress conditions are not completion, and an unreadable status is unknown.
Use generation tracking where supported to avoid interpreting an earlier
operation's conditions as the latest result. Source:
[Kubernetes 1.35 resize lifecycle](https://v1-35.docs.kubernetes.io/docs/tasks/configure-pod-container/resize-container-resources/).

### Outcomes and retries

| Observation | Required action |
|---|---|
| Patch accepted, effective tuple still old | Keep reconciling; report submitted/pending. |
| Deferred | Observe kubelet progress and report capacity dependency; avoid identical patch loops. |
| In progress | Observe actual state and runtime errors until convergence. |
| Infeasible | Report blocked; retain target and successful changes. Use rolling only if explicitly allowed. |
| Permission failure | Report exact missing permission; no silent fallback or rollback. |
| API timeout, throttling, conflict, or server error | Re-read first, then retry only needed writes with capped exponential backoff/jitter; respect server retry hints. |
| Some brokers applied, others did not | Report mixed effective state; retain successful changes and reconcile remaining brokers. |
| Higher stabilized recommendation | Persist a new target revision, then supersede old submissions without treating old status as new completion. |
| Lower recommendation during an operation | Record it, but do not begin a downward transition until the operation is resolved. |
| Broker replacement | Bind progress to the new UID/container; re-read its effective tuple and reset its observations. |
| Target/config changed after restart | Validate ownership and hash, inspect accepted operations, and rebuild observations before new writes. Never blindly replay obsolete intent. |

### Restart, configuration changes, and unfinished work

Inspect live desired/effective tuples and the operation record immediately on
startup, before fetching a full recommendation. Persist operation facts needed
to recover, not eligibility: submission timestamps/revisions may survive, while
all samples and up/down timers start empty. A lost/malformed status record with
unexplained pending or mixed resources is blocked recovery, not permission to
fabricate success or restart the down timer from old logs.

| State after inspection | Permission for new writes |
|---|---|
| Same target/config, unfinished increase | Retain and finish the committed target after rebuilding the up observation interval and safety checks described below. Lower current demand does not cancel this repair or require renewed overload. |
| Same target/config, unfinished decrease | Retain the target. Build a full fresh down-safety window against that existing target before new decreasing writes. This recovery window may run while the operation is unresolved; it does not authorize the next lower profile. |
| Already submitted Pod target | Observe kubelet progress immediately; rebuilding timers does not cancel accepted work or require an identical patch. |
| Higher sustained demand | Supersede using a new revision. Compare against every broker's actual/desired tuple; a higher name alone cannot authorize a hidden decrease. |
| Mode becomes `Off` | Observe and report the retained operation; submit no resource/strategy/retry writes. |
| Target UID or policy changes | Retain old operation facts for diagnosis, invalidate eligibility, and reconcile live state against the new policy before acting. Never apply an old target to a replacement cluster. |

For an unchanged-policy upward operation, recovery is completion of an already
committed target, not a new upward recommendation. Restart a fresh up-duration
observation interval; require at least one usable enabled signal throughout,
stable broker identity/known tuples, and confirmation that remaining writes do
not decrease any desired/effective resource. Recheck mode, capability and
permissions before writing. Lower demand may persist throughout that interval:
finish the saved target, then start the ordinary full down window. This preserves
keep-target-and-reconcile without restoring old overload history or leaving a
mixed cluster stuck when a load spike ends. All-signal unavailability still
holds; a higher stabilized recommendation can supersede. Record the action as
operation recovery, with current demand shown separately.

Changing only mode from `Off` to `Auto` with otherwise identical policy can
resume the saved target after fresh eligibility checks. For a material policy
change, adopt a matching live operation only if its exact tuple remains valid
under the new policy and identity; otherwise report incompatible operation and
stop new writes until an explicit compatible configuration is supplied. A
configuration edit is not a rollback instruction. Do not automatically lower
resources to fit a newly reduced ceiling or delete a record to escape a block.

In the same process, recheck identity, policy, metrics and memory safety before
retrying any not-yet-accepted decrease. If the down evidence has become invalid,
rebuild the full recovery window while retaining successful changes. Following
full convergence, start a separate full interval for the next lower step.

Before superseding, stop old-revision tasks, wait for or resolve their uncertain
API outcomes, re-read, then submit the latest target. Do not let a late old
request overwrite a newer target. A successful API request whose response was
lost is recovered from live state. Use optimistic concurrency for ConfigMap
updates; retain the durable intent when diagnostic status updates fail, and
pause new broker writes if that intent cannot be read/verified.

Recover drift caused by this operation; do not continually fight an external
resource writer. Unexpected third-party resource/strategy changes produce an
ownership-conflict reason and pause writes pending compatible configuration.
Supported operation assumes one scaler installation and no competing VPA,
GitOps resource writer, or manual resize of the target during an operation.

Proposal: transient write retries start at one second and cap at 30 seconds;
regular observations continue at the configured polling interval. These are
implementation defaults, not an abandonment timeout. Persisted targets survive
an overdue operation. Report deadline misses and continue reconciling; do not
call the action successful or automatically change policy to make it finish.

`Off` may write diagnostic status but must never patch broker resources, change
StatefulSet strategy, or roll brokers. A previously accepted kubelet operation
may continue after `Off` or a restart; observation must distinguish that from
a new controller action. Reset all sample history and stabilization timers,
even if the ConfigMap contains previous observations.
Recommendation-only startup must work without broker-mutation permissions;
missing resize permission is diagnostic information, not a reason to refuse `Off`.

Explicit rolling fallback delegates safe rollout sequencing to the Operator;
the concurrent-submission rule applies to the in-place path, not a request to
restart all quorum members together. Verify the Operator/StatefulSet's actual
rollout sequencing and quorum availability; a PodDisruptionBudget alone does
not constrain StatefulSet rolling updates. See [Kubernetes disruption behavior](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/).
Record fallback as a distinct restart-capable path.
Do not reinterpret a deferred resize as infeasible merely because the two-minute
objective elapsed.

Only established in-place incompatibility/infeasibility can select an authorized
rolling path; permission failures, timeouts, and unknown capability remain
blocked/retryable. Persist the path before enabling `RollingUpdate`; confirm the
template is at the intended target first, and test the strategy transition both
with and without a prior template revision. Do not add Pod deletion or broker
restart commands as an undocumented substitute. Once an authorized rollout is
submitted, `Off` cannot undo the Operator's accepted work. Return to verified
`OnDelete` before the next in-place operation; document that leaving in-place
mode installed leaves this override active for unrelated Operator upgrades.

### Status contract

Use a separate mutable ConfigMap, e.g. `<scaler-name>-status`, with a versioned
JSON snapshot. Keep it bounded and free of credentials. Store:

- Target cluster UID, config hash, controller start time, update mode, and status time.
- Ideal recommendation, eligible next action, trigger reasons, target saturation,
  stabilization state, and enabled-source freshness/completeness.
- Current durable desired target/revision and each broker's desired/effective
  CPU/memory requests and limits, UID, container ID, and resize condition.
- Per-broker errors and blocked reasons, submission/convergence timestamps,
  and deadline status. A mixed cluster is `Mixed`, not a fabricated current profile.

Use structured logs, preferably Go's standard `log/slog`, with matching target,
operation, profile, source, and broker fields. Coalesce identical observations
to avoid excessive logs and status writes. Helm must not overwrite live status
with empty defaults on upgrade.
Treat diagnostic stabilization fields as a snapshot, never restart input. Keep
operation state separate from diagnostics within the JSON document so a status
refresh cannot erase an unresolved target. Keep one active operation plus a
bounded terminal summary; logs hold older audit detail.

**Exit:** API acceptance, desired-state convergence, and effective-resource
convergence are distinct; fault-injected tests recover correctly without
accidental rolling, rollback, premature success, or unsafe new writes after restart.

### Timing protocol

The two-minute objective starts at the first fresh observation in a sustained
overload episode, not at API submission, and includes the 30-second default
stabilization period. End at confirmed effective resource convergence across
all brokers and the agreed completion checks. Preserve the original episode's
timestamps through retries; track a superseding higher target's demand separately
so it neither erases an earlier miss nor inherits an artificially short deadline.
Operation timing facts can survive a scaler restart for audit; they never
restore stabilization eligibility. A restart cannot reset an already running
deadline to hide a miss. Report detection delay from workload start separately.
The 120-second objective is tested at the default 15/30-second timings;
user-configured polling or stabilization that consumes the budget must be
reported as such, not described as meeting the default objective.

Predeclare platform capacity, health, and source completeness. Report capacity
blocks separately, with their evidence; do not retrospectively exclude an
unexplained slow resize from the healthy-case result.

Use two distinct comparisons:

1. **Native VPA baseline reproduction:** fixed two-profile CPU-request policy,
   fixed CPU limit/memory, fresh workload, five-minute load and ten-minute
   cooldown. Test the repository's controller directly against the same
   100m → 800m → 100m requirement; preserve the native test's result separately.
   Declare the Operator-managed topology change explicitly: the retained
   single-broker StatefulSet experiment is not a controlled three-broker
   performance comparison. For a matched comparison, rerun native VPA separately
   on the same Operator-managed fixture, workload, limits, and observation budget.
2. **Full 2.3 release gate:** three Operator-managed brokers, explicit requests
   and limits, and all new safety/recovery policies. Do not attribute differences
   from a changed CPU limit, message size, or workload to the recommender alone.

A four-profile ladder takes at least 15 minutes to descend three steps at the
default five-minute interval, excluding load and resize time. It is not a
universal 15-minute full-cycle promise. Use an explicitly declared two-profile
ladder for the baseline comparison; test the full ladder with its appropriate
fixed observation budget. Record saturation if a cap prevents meeting a target.


Add a dedicated new-format e2e entry point instead of silently changing the

**Exit:** local compatibility and failure tests pass; the full three-broker gate
