# Upgrading from v1

v2 is a **behaviour-identical rewrite** of the Node.js v1 in Go — same scaling
decisions, same environment-variable contract, same generated manifests, smaller
footprint. It is a drop-in replacement.

| | |
|-|-|
| **Same env-var contract** | A Deployment generated by v1 drives v2 unchanged — swap the image tag to `ferterahadi/rmq-vertical-scaler:2` |
| **Same scaling decisions** | The engine makes byte-identical decisions to v1 given the same metrics and config, enforced by a parity test |
| **Same generated manifests** | `generate` emits YAML byte-for-byte compatible with v1, except the image tag is now pinned to the release version instead of `latest`, and a PDB comment was corrected |
| **Same config format** | Existing `examples/*.json` configs work as-is |

## The one-line upgrade

```bash
kubectl set image deployment/rmq-vertical-scaler \
  rmq-vertical-scaler=ferterahadi/rmq-vertical-scaler:2 \
  -n production
```

## What you gain by doing nothing else

- Idle memory drops from ~50–80 MB to ~10–15 MB. See [why-go.md](why-go.md).
- `distroless/static:nonroot` base — no shell, no package manager, no interpreter.
- On Kubernetes 1.33+, `SCALE_MODE` defaults to `auto`, so scaling becomes
  zero-restart automatically **once the scaler has `pods/resize` RBAC**. A v1
  Deployment does not grant it, so v2 will log the missing verbs and keep rolling
  until you regenerate the manifests or add the grant by hand.

Regenerating is the simpler path:

```bash
rmq-vertical-scaler generate -c my-config.json -o scaler.yaml
kubectl apply -f scaler.yaml
```

## Staying on v1

The Node.js v1 remains available via the `v1.x` git tags and the
`ferterahadi/rmq-vertical-scaler:1.x` images. It receives no further changes.
